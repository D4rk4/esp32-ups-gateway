# Перенос интерфейса APC и API ESP32 — 0.2.0

## Что взято из референса

Источник — пользовательский `apc_hw02_aos394_rpdu_393.exe`: AOS 3.9.4 и
RPDU 3.9.3. Это карта управления распределителем питания Rack PDU. Из неё
статически извлечены 162 зарегистрированных ресурса: 127 HTML-шаблонов и
служебных фрагментов, один CSS, 33 изображения и `ddf.zip`. Восстановлены
словари сжатых строк, описания полей форм и доступные ветви шаблонов.
Контрольные суммы и ограничения разбора — в `reference/apc-webui/`.

В рабочий интерфейс перенесены основные вкладки Home / Device Manager /
Logs / Administration, боковая навигация, ширина оболочки 750 px, боковое
меню 140 px, Verdana, сине-серая палитра, оформление таблиц, оригинальные
изображения фона/вкладок и двухэтапное подтверждение команд.

**Индикатор нагрузки** основан на оригинальном APC `#gauge`: узкая
вертикальная шкала с 20 рельефными сегментами и крупным числом рядом.
Показатель — реальные проценты нагрузки ИБП. Ток, мощность в ваттах и
номинал автомата PDU не выдумываются. Зелёный означает ниже 80% настроенного
порога, жёлтый — приближение к порогу, красный — значение на пороге или
выше. Это визуальная индикация; активная тревога отдельно учитывает
превышение и настроенную задержку. Порог берётся из активного
`status.thresholds.alarm_load_high` для всех ролей. При недоступном значении
сегменты неактивны, число заменяется прочерком. Возраст отсчитывается по
`age_ms` и времени после ответа, предел берётся из активного `ups.stale_ms`;
отдельный таймер гасит индикацию даже во время зависшего HTTP-запроса.
Нагрузка выше 100% сохраняется
числом; заполнение шкалы ограничено её верхним краем.

Новый сервер и клиент написаны для общей модели UPS Gateway. Обработчики
оригинального APC `/Forms/...` не исполняются на ESP32. Название устройства
в интерфейсе — UPS Gateway; он не заявляет себя оригинальной картой APC.

## API и авторизация

Корень `/` отдаёт оболочку с формой входа. `POST /api/login` принимает
`{"username":"admin","password":"..."}` и создаёт случайную сессию
в памяти. Cookie `ups_session` имеет `HttpOnly`, `SameSite=Strict` и `Path=/`.
`GET /api/session` без входа возвращает `authenticated:false`; после входа
добавляет роль, CSRF, boot_id, версию, возможности и параметры отображения.

Изменяющие запросы после входа требуют `X-CSRF-Token` из текущей сессии.
Ответы не кэшируются. Basic auth версии 0.1.0 удалён: внешнему HTTP-клиенту
нужно войти и сохранить cookie. SNMP-опрос Observium от этого не зависит.

| Роль | Чтение состояния/журналов | Команды ИБП | Конфигурация, экспорт секретов, время, сброс, перезапуск |
| --- | --- | --- | --- |
| Read-Only User | Да | Нет | Нет |
| Device User | Да | Да, с остальными ограничениями | Нет |
| Administrator | Да | Да, с остальными ограничениями | Да |

До шести активных сессий; таблица отказов входа также ограничена. Обычные
фоновые GET не продлевают сессию. UI отмечает реальные действия человека
заголовком `X-Session-Activity: 1`; сервер проверяет роль/CSRF независимо
от состояния элементов формы. Пароли не сохраняются браузером в
localStorage/sessionStorage. HTTP не шифрует трафик; версия 0.2.0 рассчитана
на доверенную сеть управления.

Конфигурация передаётся **частичным объектом**: сохранение одной страницы
не сбрасывает остальные поля. Пустой секрет означает сохранение старого
значения. Обычный `GET /api/config` отдаёт пустые секреты и признаки
`*_set`; экспорт включает реальные секреты. Изменения действуют после
перезапуска; текущие показания используют активную копию конфигурации.
Предельное тело `/api/config` — 12288 байт, остальных POST — 2048 байт.

При сохранении нового/изменённого включённого расписания питания нужен
отдельный ввод `POWER`; подтверждение передаётся временным полем `confirm`
и не записывается в конфигурацию. То же правило действует при изменениях,
которые активируют сохранённое правило, и при импорте. Содержимое файла
импорта само по себе не считается подтверждением.

## Сохранение конфигурации и выполнение расписаний

Исторически в версии 0.2.0 использовался один `factory` по 0x10000 размером
0x3F0000 и `appcfg` по 0xF00000 размером 0x10000. Актуальная OTA-разметка,
однократный переход по USB и правила обновления описаны в [OTA_RU.md](OTA_RU.md).
Адрес и размер `appcfg` не изменены. UI встроен в приложение; раздел `logs`
только зарезервирован и не является файловой системой.

Config схемы 1 мигрирует в схему 2 в памяти с сохранением прежних секретов.
Автоматического стирания NVS при ошибке нет. Планировщик хранит в отдельном
пространстве имён того же appcfg отметки попыток исполнения. Он сохраняет
отметку до постановки команды в очередь, не повторяет её после неопределённого
результата и не выполняет пропуски задним числом. При рестарте/скачке часов
действует защитное окно. Наличие допустимого времени не подтверждает
физическое исполнение команды; состояние `sent_unconfirmed` означает только
передачу байтов. Точное поддерживаемое UTC-окно возвращается `/api/time`. В зафиксированном
Arduino ESP32 2.0.17 / toolchain этого выпуска `time_t` имеет 32 бита: верхняя
граница — 19 января 2038, 03:14:07 UTC. UI читает этот предел из API.

## Границы переноса

В этой версии отсутствуют SMTP/email, HTTPS/управление сертификатами,
SNMPv1/v3, INFORM, RADIUS, SSH/Telnet, FTP/SCP, WAP и WoL. Соответствующие
службы APC нельзя включить неработающим переключателем. В разделе
возможностей перечислены неподдержанные службы. Не реализованы полная
матрица индивидуальных действий для каждого события APC, ротация журнала
на FTP, синхронизация групп карт и модель независимых PDU-розеток/банков.
Шлюз предоставляет общие пороги, фильтрацию syslog и два получателя traps.

Это явные границы данного выпуска, а не утверждение, что перенесены все
сервисы сетевой карты APC. Новые выходные группы и другой протокол ИБП
нужно добавлять через расширение общей модели и драйвера, затем API/UI.

## Как проверять UI

`tests/ui_fixture.html` — автономный стенд с синтетическими ответами API и
реальным клиентским кодом `web/index.html`. Он не входит во встроенный
web-ресурс прошивки, не обращается к ESP32 и явно помечает тестовые данные.
Переключатели стенда создают нормальную/высокую нагрузку, потерю RS232,
ошибку HTTP и завершение сессии. Такой стенд позволяет проверять клиентские
сценарии, но не заменяет аппаратную проверку.

Окончательные результаты сборки, тестов и доступности браузерной проверки
описаны в `BUILD_REPORT.md`. Скриншоты допустимо считать проверкой только
после фактического отображения страницы в браузере.
